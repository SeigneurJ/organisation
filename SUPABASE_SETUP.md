# Préparer Supabase pour Organisation

Cette intégration permet de retrouver les mêmes tâches, habitudes, notes et encarts sur plusieurs appareils après connexion au même compte. Le compte et les mots de passe sont gérés par Supabase Auth. Les données de l’application sont conservées dans une ligne Postgres propre à chaque compte.

## État du projet

Le projet Supabase `organisation` existe en région Irlande (`eu-west-1`). Les migrations 001, 002 et 003 ont été exécutées. La fonction Edge `username-auth` est déployée avec `verify_jwt = false`, explicitement autorisé, et les origines autorisées ainsi que l’URL de redirection de récupération ont été enregistrées dans la configuration Edge. Les clés gérées par Supabase sont injectées; aucune clé secrète n’est consignée dans ce dépôt. Le contrôle SQL agrégé en lecture seule confirme `base_access_setup_ready = true`, `username_auth_migration_003_present = true` et `admin_count = 1`. Le smoke test de la fonction a confirmé une réponse CORS 204 pour l’origine attendue, une erreur 400 pour un JSON invalide et une erreur 401 pour une attribution d’identifiant sans JWT. Ces contrôles n’ont créé aucun compte, envoyé aucun courriel ni modifié de données applicatives. La configuration Gmail du SMTP est préparée mais n’a pas encore été enregistrée ni validée. Le lot local de code et de documentation n’a pas encore été publié sur GitHub Pages.

Le script en lecture seule [`supabase/verify_access_approval_readonly.sql`](supabase/verify_access_approval_readonly.sql) a été exécuté dans Supabase sans erreur. Le panneau SQL n’affichant que le dernier résultat, la sortie visible a confirmé `admin_uuid_has_unique_primary_key = true`. La requête de comptage des administrateurs a aussi été exécutée séparément : `admin_count = 1` et `exactly_one_admin_registered = true`. Les résultats intermédiaires du script (tables/RLS, privilèges et signatures RPC) ne sont pas consignés comme vérifiés. Les parcours avec plusieurs comptes et les tentatives d’accès direct avec un JWT encore valide restent à tester.

Le mode local reste utilisable sans configuration. Il conserve les données dans le navigateur de l’appareil. Le fichier ouvert en `file://` ne peut pas synchroniser les données; il faut ouvrir l’application hébergée en HTTPS sur l’ordinateur et le portable.

## Configuration du projet

1. Ouvrez le projet Supabase `organisation` existant en région Irlande (`eu-west-1`).
2. La migration [`supabase/migrations/202610220001_create_organisation_states.sql`](supabase/migrations/202610220001_create_organisation_states.sql) est déjà exécutée. Réexécutez-la seulement si vous recréez le projet ou son schéma.
3. La migration d’approbation [`supabase/migrations/202610220002_access_approval.sql`](supabase/migrations/202610220002_access_approval.sql) a été exécutée. Ne la réexécutez pas manuellement hors d’une procédure de reprise du projet.
4. Le compte propriétaire a été invité dans **Authentication → Users**, puis son UUID Auth a été vérifié dans cette liste. Le bootstrap administrateur a été appliqué avec cet UUID vérifié : il l’inscrit dans `organisation_private.organisation_admins` et approuve sa demande. Le modèle [`supabase/bootstrap_admin.template.sql`](supabase/bootstrap_admin.template.sql) conserve volontairement un UUID zéro de remplacement et échoue s’il est exécuté tel quel; ne remplacez pas ce placeholder dans le fichier versionné.
5. Le flux d’inscription peut être ouvert avec confirmation d’e-mail activée, ou rester sur invitation uniquement. Dans les deux cas, les nouveaux Auth users restent `pending` jusqu’à approbation. Le trigger de la migration crée la demande sans accorder d’accès aux données.
6. L’URL du site et les URL de redirection Auth ont été configurées. Pour GitHub Pages, l’URL autorisée est `https://seigneurj.github.io/organisation/`; vérifiez ces réglages si le domaine ou le chemin change.
7. L’URL du projet et la clé publishable sont déjà renseignées dans `index.html`. Vérifiez qu’elles correspondent au projet `organisation`; ne remplacez ces valeurs que si le projet cible change.
8. Le script [`supabase/verify_access_approval_readonly.sql`](supabase/verify_access_approval_readonly.sql) a été exécuté. Son contrôle complet actuel est consigné ci-dessus dans l’état du projet. Le script [`supabase/verify_project_status_readonly.sql`](supabase/verify_project_status_readonly.sql) fournit les vérifications agrégées après la migration 003. Les parcours utilisateur `pending`, `approved`, `rejected` et `suspended`, y compris les requêtes directes avec un JWT encore valide, restent à valider.
9. La migration [`supabase/migrations/202610220003_username_auth.sql`](supabase/migrations/202610220003_username_auth.sql) a été exécutée avec succès. Le contrôle en lecture seule confirme les objets d’authentification par identifiant attendus.
10. La fonction [`supabase/functions/username-auth/index.ts`](supabase/functions/username-auth/index.ts) est déployée. `verify_jwt = false` a été explicitement autorisé pour que la fonction traite aussi les demandes avant connexion; elle vérifie elle-même les entrées et exige une session pour attribuer un identifiant. Les origines autorisées et `AUTH_PASSWORD_RESET_REDIRECT_URL` sont sauvegardés dans les secrets Edge. Supabase injecte `SUPABASE_URL` et ses clés gérées; ne copiez aucune clé secrète dans une variable personnalisée ou dans le dépôt. Le smoke test a vérifié CORS pour l’origine attendue, le rejet d’un JSON invalide et le rejet d’une attribution sans JWT. Aucun compte ni donnée applicative n’a été modifié et aucun courriel n’a été envoyé. Supabase Auth conserve ses limites natives; sans transfert d’adresse IP explicite, ses limites par IP peuvent être partagées par les connexions passant par la même fonction Edge. Voir la documentation Supabase sur les [variables d’environnement Edge](https://supabase.com/docs/guides/functions/secrets) et la [migration vers les nouvelles clés API](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys).
11. La configuration Gmail du SMTP est en cours de saisie privée dans le tableau de bord Supabase; elle n’est pas encore enregistrée ni validée. Ne consignez pas le mot de passe d’application Google dans le dépôt. Une fois le SMTP validé, Jérémie pourra se connecter avec son adresse e-mail et son mot de passe Supabase (ou utiliser la récupération de compte) pour choisir son identifiant. Le modèle [`supabase/bootstrap_username.template.sql`](supabase/bootstrap_username.template.sql) permet une attribution manuelle au compte propriétaire si nécessaire; son UUID et le nom choisi ne doivent être ajoutés qu’à une session SQL privée, jamais au dépôt. Les nouveaux utilisateurs confirment leur e-mail, se connectent, choisissent un identifiant, puis attendent l’approbation. L’identifiant accepte 3 à 32 caractères ASCII, commence par une lettre et peut ensuite contenir lettres, chiffres, point, tiret bas ou tiret; la comparaison ignore la casse. Le nom affiché peut conserver les accents.

La clé publishable est conçue pour être utilisée côté navigateur; elle ne remplace pas les règles d’accès. **N’ajoutez jamais une clé `service_role`, une clé secrète, un mot de passe ou un hash de mot de passe dans `index.html`, les fichiers de configuration publics ou GitHub.** Le script `supabase-js` est chargé depuis jsDelivr et nécessite une connexion Internet en mode en ligne.
